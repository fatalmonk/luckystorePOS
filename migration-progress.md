# Customer storefront native migration progress

Assessment date: 2026-10-08. Source baseline: `main` at `0e971f12210a642fca52a561aefe222d1e772f60`. Target: a separate Expo customer app at `apps/customer_mobile` for iOS and Android. Backend decision: keep `apps/customer_storefront` deployed as the website and HTTPS backend; native uses the absolute base URL `https://www.luckystore1947.com`.

This is the durable goal-loop worklist. Each pass resolves exactly the first unchecked **nativize-now** item. `en` and `bn` web route pairs map to one native screen with locale state. Existing server `route.ts` handlers, database code, SEO routes, admin code, and the Flutter operations app are not copied into the native bundle.

## Prerequisites and invariants

- The first Home pass also scaffolds the minimal Expo Router shell because `apps/customer_mobile` does not yet exist.
- Native data calls use a configured absolute HTTPS API URL. The device never receives privileged database keys or imports server-only modules.
- The npm workspace pins Expo 57, Expo Router, React Native, Reanimated, Worklets, Gesture Handler, Safe Area Context, and Screens at the repository root so the hoisted Expo CLI resolves the same native toolchain as `customer_mobile`.
- Expo Doctor currently passes 20/21 checks. Its remaining warning is the React/React DOM split: Expo requires `19.2.3`, while existing web workspaces resolve `19.2.7`; native device builds must validate this boundary before release.
- Native owns locale, cart, auth/session, checkout attempt identity, and guest tracking capability. DOM content cannot own or receive those secrets.
- Checkout keeps server-authoritative prices, stock, tenant/store binding, and transaction/idempotency rules. Verification never submits against production.
- `agent-browser` and `argent` are installed and required before screen parity can be marked done.
- iOS runtime verification requires a full selected Xcode installation; current `xcodebuild` points to Command Line Tools. Argent currently reports no iOS devices or Android AVDs.
- Keep the app build green each pass. A compile/export alone cannot satisfy a screen's verification gate.
- Unrelated existing changes (`context.md` and `lucky-store-brand-guidelines/social-media-post/`) remain untouched.

## port-as-is

No whole-screen DOM/WebView ports are selected for release. Small audited informational content components may use Expo DOM inside a native route after proving they receive only sanitized DTOs and no session/cart capability.

## hybrid

- Delivery, Privacy, Terms and Security Policy: native route/navigation with optional reviewed DOM content body.
- Product detail: native screen/actions; a presentational DOM component may be used only during the initial bridge proof and is not the release interaction owner.

- `(english)/fortune-cookies-near-me/page.tsx` and `(bengali)/bn/fortune-cookies-near-me/page.tsx`: SEO landing pages; app links resolve to supported product/category routes.
- `(english)/preview/page.tsx` and `(english)/preview/shop/page.tsx`: internal web previews; excluded from release navigation.
- Metadata, robots, sitemap, JSON-LD, install prompt, GTM/Zaraz and other browser marketing scripts.
- All existing API, webhook, auth callback and `.well-known`/discovery `route.ts` handlers remain server-side. New versioned mobile endpoints are added only as screen contracts require them.

- Route inventory: 30 page screens (21 English-group, 9 Bengali-group), 9 `app/api` handlers and 7 discovery/document handlers were classified in the detailed audit.

- Known gates: native bearer auth contract, bounded catalog/detail/mobile policy APIs, public-store visibility regression, checkout retry/capability storage, customer deletion operations and native tooling.
